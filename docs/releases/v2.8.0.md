# v2.8.0

Two fixes that change **where the official Codex CLI keeps its state**, plus a diagnostic that can now repair the first one instead of only reporting it.

The headline is macOS asking you to unlock the login keychain over and over, no matter how many times you clicked "Always Allow". The cause was never this project's own storage — that has always been plain JSON — but a setting in the official CLI's config that this wrapper only fixed lazily.

This is a minor release rather than a patch because it changes behaviour rather than only correcting it: the wrapper now writes `cli_auth_credentials_store` into `~/.codex/config.toml` on first run and on wrapper startup, where before it only did so during an account switch, login, health check, or repair. There is an opt-out if you want the old behaviour.

Closes [#641](https://github.com/ndycode/codex-multi-auth/issues/641). Landed as [#642](https://github.com/ndycode/codex-multi-auth/pull/642), [#639](https://github.com/ndycode/codex-multi-auth/pull/639), and [#643](https://github.com/ndycode/codex-multi-auth/pull/643).

## Credential storage

### Repeated macOS login-keychain prompts

CodexBar — and any other front-end that runs the official `codex` binary directly — kept triggering the login-keychain prompt, and "Always Allow" never made it stop.

None of this project's own state touches the keychain. The prompts come from the **official** CLI, which reads `cli_auth_credentials_store` from `~/.codex/config.toml`. When that is `"keychain"`, it reaches into the login keychain on every launch.

The wrapper already appended `-c cli_auth_credentials_store="file"` to every command it forwarded, but that only covers processes the wrapper itself spawns. A menu-bar app or editor extension that execs the official binary reads `config.toml` instead — so the *persisted* value is the one that decides. And persisting it was lazy: it only happened inside a switch, login, health check, or repair. Install the package, drive Codex through a third-party front-end, and you could sit on the keychain store indefinitely.

The value is now reconciled proactively — at first-run setup, and again as an idempotent guard on wrapper startup, which also self-heals a config that something else flipped back (a fresh official `codex login`, for instance).

Only the **top-level** assignment is touched. A `cli_auth_credentials_store` inside a `[profiles.*]` table is left exactly as you authored it, and a top-level key is inserted above the first table instead. The rewrite preserves the file's existing line endings, and both TOML string forms are recognised, so `'file'` counts as already-correct and is left alone.

Nothing reads or deletes keychain items. Doing so would itself raise the prompt this release exists to remove. Credentials saved by an earlier official `codex login` stay where they are, are simply no longer read, and can be cleared by hand in Keychain Access ([#642](https://github.com/ndycode/codex-multi-auth/pull/642)).

### `doctor --fix` repairs the credential store

The `codex-auth-store` check already warned when the store was not pinned to `"file"`, but `--fix` had no remediation for it — the warning was unactionable unless you happened to also have an account to sync.

`codex-multi-auth doctor --fix` now pins it directly and re-reports the check as `ok`. `--fix --dry-run` reports what it *would* do, like every other fix. On macOS, once pinned, the check also notes that credentials from an earlier official `codex login` may still be sitting in the login keychain, are no longer read, and can be removed manually.

The fix is also reported correctly on a machine with **no accounts registered yet** — previously the summary said nothing had changed even after rewriting the config, which is exactly the state someone hitting these prompts tends to be in ([#642](https://github.com/ndycode/codex-multi-auth/pull/642)).

## Interactive sessions

### Session history reindexed on every launch

Starting an interactive session with runtime rotation enabled copied your Codex home into a temporary shadow directory, ran there, and synced state back on exit. That made the official CLI reindex session history on every launch, and put a copy-and-sync-back step in the path of your real session state.

Interactive sessions now run against the canonical `CODEX_HOME` and receive the rotation provider through `-c` overrides instead. Session history and SQLite state are read and written in place, so there is nothing to reindex and nothing to sync back.

The rotation provider itself is no longer written into any config file on this path — it travels entirely as `-c` overrides. Your real `config.toml` is still subject to the credential-store reconcile described above, which may update the top-level `cli_auth_credentials_store` key on startup; nothing else in it is touched.

Non-interactive commands, `codex app`, and `app-server` are unchanged and still use the shadow home.

Because interactive sessions now share the canonical home, two of them can run at once against the same state — the same as running the official CLI twice. No lock is taken: nothing on this path copies or syncs state, so there is nothing to clobber, and serialising sessions would be a regression against how the official CLI already behaves ([#639](https://github.com/ndycode/codex-multi-auth/pull/639), [#643](https://github.com/ndycode/codex-multi-auth/pull/643)).

## Upgrade notes

Nothing to do. The first `codex-multi-auth` or wrapper invocation after upgrading reconciles `~/.codex/config.toml` for you.

If you were already installed before this release, the first-run marker is migrated in place: only the new credential-store step is replayed, and app bind and launcher install are deliberately **not** rerun, so shortcuts you removed stay removed. A step that fails — a locked or read-only `config.toml`, for instance — leaves the marker unmigrated so the next run retries, rather than recording the work as done.

Two opt-outs, both documented in [docs/configuration.md](../configuration.md):

| Variable | Effect |
| --- | --- |
| `CODEX_MULTI_AUTH_ENFORCE_CLI_FILE_AUTH_STORE=0` | Never write `cli_auth_credentials_store` into `config.toml` — first run, wrapper startup, account sync, and `doctor --fix` |
| `CODEX_MULTI_AUTH_FORCE_FILE_AUTH_STORE=0` | Stops the wrapper specifically: no startup reconcile, and no per-invocation `-c cli_auth_credentials_store="file"` on the commands it launches |

Set the **first** to keep your `config.toml` untouched — that is what front-ends like CodexBar read, so it is the one that restores keychain behaviour for them. Note it does not stop the wrapper from passing `-c cli_auth_credentials_store="file"` to sessions it launches itself, so those still use the file store.

Set **both** if you want the keychain store everywhere, including sessions launched through the wrapper.
