# v2.8.5

A corrective release. No new features and no configuration migration.

Runtime rotation app helpers could outlive their idle timeout without bound. On the machine that reported it, 183 of them were resident at 5.58 GB, the oldest 33 hours past a 12-hour timeout, and the machine was in swap thrash. Alongside them sat 579 orphaned owner files — later measured at 701 against 3 live helpers — and a single shared status file being atomically rewritten roughly 183 times a second.

Every defect below dates to the commit that introduced the runtime rotation proxy and was present on every release since.

Closes [#663](https://github.com/ndycode/codex-multi-auth/issues/663), [#666](https://github.com/ndycode/codex-multi-auth/issues/666), [#667](https://github.com/ndycode/codex-multi-auth/issues/667), and [#668](https://github.com/ndycode/codex-multi-auth/issues/668). Landed as [#664](https://github.com/ndycode/codex-multi-auth/pull/664), [#665](https://github.com/ndycode/codex-multi-auth/pull/665), and [#669](https://github.com/ndycode/codex-multi-auth/pull/669).

Reported with a complete diagnosis, a deterministic reproduction, and the original patches by [@possibilities](https://github.com/possibilities), who also filed the three follow-ups. The OpenAuth removal is from [@sussdorff](https://github.com/sussdorff) in [#661](https://github.com/ndycode/codex-multi-auth/pull/661).

## The leak

### A recycled PID made a helper immortal

Each helper watches its launcher so it can tell "my owner is still working" from "my owner is gone". That check was a bare `kill(pid, 0)`, which answers *does some process hold this integer*, never *is this still my launcher*. macOS recycles PIDs aggressively and a busy machine churns hundreds of short-lived processes an hour, so a helper would eventually mistake an unrelated process for its owner and treat it as activity:

```js
if (ownerPid && isRuntimeRotationAppHelperOwnerAlive(ownerPid)) {
    lastActivityAt = currentTime;   // deadline pushed out another 12 hours
}
```

The deadline only ever moved forward, so a single false "alive" was never corrected by later true "dead"s. One leaked helper's status showed `lastActivityAt` bumped 5.5 hours after `startedAt` with zero requests served — only this branch can have done that, and its owner was long dead.

Owner identity is now the PID **plus the launcher's kernel start time**, captured at spawn. A recycled PID necessarily has a later start time, so the match fails and the helper correctly sees a dead owner. The re-check runs at most once a minute and is single-flight, so a wedged `ps` holds one child rather than one per tick, and a failed read keeps the previous verdict rather than declaring a live owner dead — under the process-table pressure this exists for, `fork` itself can fail.

Windows has no `ps` and therefore no start-time source. The probe short-circuits there rather than spawning a process that could only fail, and owner liveness runs on bare `kill(pid, 0)` with the lifetime ceiling below as the bound.

### Nothing else bounded a helper's life

Any bug in activity accounting produced an *unbounded* leak, because the idle check was the only exit. There is now an absolute ceiling, `CODEX_MULTI_AUTH_APP_ROTATION_MAX_LIFETIME_MS`, default 24 hours, `0` to disable. It is deliberately unconditional on activity: it exists for exactly the case where activity accounting is wrong, and it turns any future accounting bug into a bounded leak instead of an unbounded one.

### Helpers stranded by the detach grace

A launcher that exits cleanly within a five-second window leaves its helper running, which is how `codex app` hands the desktop app a working proxy. Every short forwarded command took the same path, stranding a helper that then held the full 12-hour timeout with no owner, no traffic, and nothing connected.

A shorter window now applies once the owner is *confirmed* dead: `CODEX_MULTI_AUTH_APP_ROTATION_DETACHED_IDLE_MS`, default 15 minutes, `0` to restore the previous behaviour.

It only reaps a helper that has **never served a request**, and that gate matters more than it looks. The proxy leaves `keepAliveTimeout` at Node's 5-second default, so a `codex app` session that is merely idle between turns holds no socket within seconds of its last turn — reaping on the socket check alone would kill a working proxy out from under the desktop app, and the next message would get ECONNREFUSED against a dead localhost port with nothing left to restart it. Every helper in the leak report had `totalRequests: 0`, so the narrower gate closes the leak in full. A helper that served anything was genuinely handed off and falls back to the idle timeout and the ceiling.

"No owner PID was recorded" and "the owner is confirmed dead" are also kept distinct. Collapsing them would start the detached clock on the first tick for a helper invoked directly or spawned by a pre-upgrade launcher, and reap it silently fifteen minutes later.

### One status file, N writers, 1 Hz

`resolveRuntimeRotationAppHelperStatusPath` returned a single shared path with no PID component, and every helper rewrote it from every tick. The file described an arbitrary helper — last writer wins — so `rotation status` and runtime account resolution reported a random or dead helper whenever several ran, which is routine with one account-pinned `app-server` per account. It was also real I/O that scaled linearly with the leak.

Helpers now publish `runtime-rotation-app-helper.<pid>.json`, one per helper, and publish only on change plus a heartbeat rather than every tick. The un-suffixed legacy path is still read so a pre-upgrade helper stays visible.

### Owner files were written and never removed

`runtime-rotation-app-helper-owner.<pid>.json` was created per helper and nothing deleted it. A helper now removes its own on exit, and each launcher sweeps metadata whose helper PID is dead — after spawning its own helper, so the synchronous sweep never sits in front of `codex app` or TUI startup.

`codex-multi-auth rotation unbind-app` reclaims the same metadata independently, including owner files with no surviving status record. That is the only repair path on a machine that has stopped launching helpers, which is exactly the state a user reaches after hitting this bug and giving up.

## `rotation status` accuracy

### Unbind could orphan an owner file permanently

Two branches removed a status file without checking ownership but gated the owner-file removal on it. When the two identity tokens disagreed, unbind deleted the status file and kept the owner file — and because unbind then enumerated status paths only, nothing ever rediscovered it.

A proven-dead PID now removes both, which is what the launcher-side sweep already did, so the two paths agree. The ownership gate still stands where it matters: a *live* PID whose ownership cannot be verified is preserved with a warning and never signalled.

### Two selectors that could disagree with each other

"Which helper is current" was implemented twice, in the rotation command and in runtime account resolution, each hand-rolling its own recency sort and liveness filter. A single `rotation status` run executed both — and selected twice, either side of an awaited call — so a helper that exited during that await could be named on the status line while a different one fed the `current` account marker two lines down.

Both now use one selector. `rotation status` selects once and threads a single instant through the status line, the live count, and the account marker.

Neither copy checked process identity, which was the substantive half. A stale legacy status file whose PID has since been recycled passes `kill(pid, 0)` and could be selected as the current helper, pinning the UI to an account no helper is using. Liveness now also requires the record to be fresh: a running helper republishes at least once per heartbeat, so ten heartbeats of silence means the current holder of that PID did not write that file. Freshness rather than a kernel start-time probe because both call sites are synchronous read-only status paths reached from the interactive menu as well as the CLI.

Both readers also accepted any finite number as a PID, so a corrupt or hand-edited record carrying `-1234` reached `process.kill(-1234, 0)` — a POSIX process-*group* probe that succeeds on any busy machine and reports a helper that does not exist as live. PIDs are now validated as positive integers, matching the check the app-bind reader already applied.

## Packaging and dependencies

`@openauthjs/openauth` is removed. It was used for one function, PKCE pair generation, which is now derived directly from `node:crypto`: a 64-byte random verifier as base64url, and `BASE64URL(SHA256(ASCII(verifier)))` as the challenge, per RFC 7636. A test pins the verifier length and alphabet and the exact challenge derivation ([#661](https://github.com/ndycode/codex-multi-auth/pull/661)).

The published wrapper's fault injectors are also gated. `scripts/codex.js` ships to every install, and its test-only failure counters were read unconditionally from the environment and parsed with `Number.parseInt`, which reads `"2abc"` as 2 and `"1e3"` as 1. All seven now require an explicit `CODEX_MULTI_AUTH_TEST_FAULT_INJECTION=1` alongside a strictly numeric value, so a stray variable in a shell profile or CI environment cannot arm one — which for the metadata cleanup injector would have silently defeated the first N deletions of every sweep.

## Upgrade notes

No migration is required, and no existing settings were renamed or repurposed:

```bash
npm i -g codex-multi-auth
codex-multi-auth --version
```

That should report `2.8.5`.

If you have been hit by this, check for accumulated helpers and metadata before doing anything else:

```bash
ps ax | grep -c 'codex-multi-auth-runtime-app-helper'
ls ~/.codex/multi-auth/runtime-rotation-app-helper*.json | wc -l
```

Then reclaim them:

```bash
codex-multi-auth rotation unbind-app
```

That stops every helper it can prove is yours and removes their metadata, including owner files whose status record is already gone. Records for live PIDs whose ownership it cannot verify are preserved with a warning rather than signalled.

Two new environment variables, both optional:

| Variable | Default | Effect |
| --- | --- | --- |
| `CODEX_MULTI_AUTH_APP_ROTATION_MAX_LIFETIME_MS` | 24h | Absolute ceiling on a helper's life, unconditional on activity. `0` disables. |
| `CODEX_MULTI_AUTH_APP_ROTATION_DETACHED_IDLE_MS` | 15m | Idle window applied once the owner is confirmed dead, nothing is connected, and the helper has never served a request. `0` restores the full idle timeout. |

Three consequences worth knowing rather than discovering:

- Helper status files are now per-PID. Anything reading `~/.codex/multi-auth/runtime-rotation-app-helper.json` directly should read `runtime-rotation-app-helper.<pid>.json` instead; the legacy path is still read by this package but is no longer written.
- On Windows there is no kernel start time available, so owner identity degrades to bare liveness and the 24-hour ceiling is what bounds a leak.
- A helper that has served at least one request is no longer reaped by the detached window. It falls back to the idle timeout and the ceiling, which is the behaviour that existed before that window.

## Regression coverage

The lifecycle paths are covered by wrapper tests that drive real helper processes: the detached window firing on a stranded helper and *not* firing on one that served traffic, a helper launched without an owner PID staying on its idle timeout, the ceiling stopping a helper whose owner is alive, owner-file removal on exit, and the launcher sweep.

Dead and live PIDs in those fixtures are processes the tests own and reap rather than integers above the platform ceiling, and the second live PID is a process the test controls rather than the vitest pool's parent — both of which were previously true only by accident.

A stress suite exercises the same code at the scale the report described: unbind over 250 dead records and orphaned owner files with live helpers preserved, 700 stale files swept on one launch, 30 launch/exit cycles asserting metadata plateaus rather than climbing, ten concurrent helpers keeping separate status files, a five-way reap matrix run simultaneously, readers hammering the directory while unbind deletes underneath them, and a directory of malformed metadata including truncated JSON, a 2 MB record, negative and fractional PIDs, and directories and symlinks where records belong.

The suite was mutation-checked: reverting the never-served gate, the owner-verdict distinction, the orphan enumeration, the launcher sweep, or the unbind concurrency bound each fails a specific test.

The full local suite passed with 340 test files passing and 1 skipped, for 5,440 tests passing and 19 skipped. The skipped count rises from 4 in v2.8.4 because the new helper-lifecycle tests are POSIX-only and are counted as skipped on the platform these numbers are measured on; they run and pass on Linux.
